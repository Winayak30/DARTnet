# NEXUS SOC — UI Redesign + Backend Improvement Plan

## Top-Level Overview

NEXUS SOC is a passive, AI-assisted network threat detection platform built with React 18 + TypeScript (frontend), Spring Boot 3.2 (backend), FastAPI + scikit-learn/XGBoost (ML service), and PostgreSQL. The system currently works end-to-end but uses a light-gray enterprise look that undersells the product for a hackathon pitch.

This plan covers two tracks running in parallel:

**Track A — UI Redesign:** Replace the current light-gray CSS design system with a dark cyberpunk design system inspired by VigilAI (Image 3) as the primary reference, using structural elements from Blockchain Secure (Image 2) for the hero, Ackee (Image 4) for feature cards and stat callouts, and the Cyber Security Expert (Image 1) for the color palette. No new pages are added; existing routes stay the same. Only global CSS tokens, layout components (Sidebar, TopBar), shared UI components (KpiCard, AlertTable, Badges), and page-level visual structure are changed.

**Track B — Backend Improvements:** Fix the five most impactful backend gaps without breaking existing functionality: (1) multi-label detection so a flow can trigger more than one detector, (2) fix the `isThreat=false` confidence discard bug so ML confidence always contributes to fusion, (3) make detection thresholds configurable via `application.yml`, (4) fix the WebSocket connected-state timer with real STOMP lifecycle events, and (5) expose the `PIPELINE_UPDATE` event in the frontend reducer.

## What the Models Actually Do

| Model | Algorithm | Features Used | What It Detects | Synthetic F1 |
|---|---|---|---|---|
| DDoS/SYN Flood | RandomForest | flow_rate, packet_rate, syn_ratio, unique_source_ips, source_entropy, dest_concentration, mean_packet_size, packets, bytes, duration_ms, syn_count | High SYN ratio + many sources flooding a single destination | 0.959 |
| Port Scan | RandomForest | unique_dest_ports, unique_dest_hosts, fan_out, connection_rate, failed_connections, syn_without_ack, packet_count, duration_ms | One source probing many ports/hosts | 0.977 |
| DNS/DGA | RandomForest | domain_length, entropy, digit_ratio, consonant_ratio, unique_char_ratio, ngram_anomaly_score, query_rate, subdomain_depth, tld_suspicion | High-entropy domain names generated by DGA malware | 0.936 |
| C2 Beaconing | XGBoost | mean_inter_arrival_ms, inter_arrival_variance, periodicity_score, connection_count, unique_dest_count, flow_duration_ms, bytes_per_flow, small_packet_ratio | Periodic low-volume connections consistent with C2 check-ins | 0.952 |
| Data Exfiltration | RandomForest | outbound_bytes, inbound_bytes, outbound_inbound_ratio, flow_duration_ms, dest_concentration, transfer_rate_bps, burst_count | Massive outbound-to-inbound byte ratio to a concentrated destination | 0.926 |
| Encrypted Traffic | Rules only (no ML) | Packet size stats, TLS metadata, timing | Anomalous encrypted traffic patterns | N/A |

**Score fusion:** `final_score = 0.4 * rule_score + 0.6 * ml_score`. If ML is unavailable, rule score is used directly.

**Known gap:** All metrics are on synthetic data. Real-world accuracy is unknown.

## Track B — Backend Improvements

### Sub-Task B1 — Fix Multi-Label Detection

**Intent:** The current orchestrator uses an `if / else if` chain, so a flow that qualifies for both DDoS and exfiltration (for example) only generates one alert. Change to independent evaluation so all qualifying detectors run.

**Expected Outcomes:**
- All five detector methods run independently for each flow
- A flow can produce 0, 1, or multiple alerts in a single `processFlow` call
- Each detector checks `alertedFlows` independently so repeat alerts per flow per detector are still suppressed
- No existing detector logic changes — only the control flow in `processFlow`

**Todo List:**
1. Change `processFlow` in `DetectionOrchestrator.java` from `if/else if` chain to sequential independent `if` blocks with independent `Optional<AlertDTO>` per detector
2. Collect all non-empty alerts into a list and persist each one
3. Update `alertedFlows` key from `flowId` to `flowId + ":" + detectorType` so each detector tracks independently
4. Add a unit test covering a flow that qualifies for both DDoS and exfiltration conditions

**Relevant Context:**
- `backend/src/main/java/com/nexussoc/service/DetectionOrchestrator.java:60-88` — current if/else if chain
- `backend/src/main/java/com/nexussoc/service/DetectionOrchestrator.java:40-45` — `alertedFlows` Set

**Status:** [ ] pending

### Sub-Task B2 — Fix ML Confidence Discard Bug

**Intent:** Currently `runMlInference` returns `0.0` when `isThreat == false`, which the fusion function treats as "ML unavailable" and falls back to rule-only scoring. This means low-confidence ML predictions are silently discarded. Fix so the raw confidence value is always passed to fusion, and the `isThreat` flag is only used for logging/evidence.

**Expected Outcomes:**
- `runMlInference` returns `mlResponse.getConfidence()` regardless of `isThreat` value
- Score fusion always uses `0.4 * rule + 0.6 * ml` when ML responds, even if ML confidence is low
- A flow with rule score 0.6 and ML confidence 0.1 gets fused score 0.30 (correct — below threshold, no alert)
- A flow with rule score 0.8 and ML confidence 0.3 gets fused score 0.50 (correct — exactly at threshold)
- Add a log entry at DEBUG level recording both scores and fused result

**Todo List:**
1. In `DetectionOrchestrator.java:runMlInference`, remove the `.filter(MlContract.PredictResponse::getIsThreat)` and return `getConfidence()` directly when the response is present
2. Update `fuseScores` doc comment to clarify that `mlScore == 0.0` specifically means ML was unavailable (no response/exception), not low confidence
3. Add debug log in `fuseScores` showing ruleScore, mlScore, fusedResult

**Relevant Context:**
- `backend/src/main/java/com/nexussoc/service/DetectionOrchestrator.java:423-437` — `runMlInference`
- `backend/src/main/java/com/nexussoc/service/DetectionOrchestrator.java:408-421` — `fuseScores`

**Status:** [ ] pending

**Expected Outcomes:**
- `wsConnected` is set `true` only after a successful STOMP `onConnect` callback
- `wsConnected` is set `false` on STOMP `onDisconnect` or `onStompError`
- The TopBar "LIVE" indicator accurately reflects actual WebSocket state
- Reconnection attempts set it back to `true` on success

**Todo List:**
1. Update `frontend/src/hooks/useWebSocket.ts` to accept optional `onConnect` and `onDisconnect` callbacks
2. In `frontend/src/App.tsx`, pass `onConnect: () => dispatch({ type: 'SET_WS_CONNECTED', payload: true })` and `onDisconnect: () => dispatch({ type: 'SET_WS_CONNECTED', payload: false })` to `useWebSocket`

**Relevant Context:**
